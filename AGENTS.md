# AGENTS.md

This file is the index for agents working in this repo. It holds only one-line rules that prevent a recurring defect class (each naming its guardrail or depth doc), everyday commands, and a map of every doc. Everything else lives in a named home in this repo (CONTRIBUTING.md, `docs/`, a workflow's own comments). Never add narration, history, backlog items, drifting figures, code trivia an agent can grep, or a second copy of a fact that already has a home. A line found in the wrong place moves home in the change that finds it, leaving the rule and a pointer.

## Commands

- `npm ci`: install (npm, `package-lock.json`)
- `npm test`: build, then run the integration suite in a downloaded VS Code (opens a VS Code window; on headless Linux run `xvfb-run -a npm test`)
- `npx tsc --noEmit -p .`: typecheck (`npm test` bundles with esbuild, which does not typecheck)
- `npm run lint` / `npm run format`: Prettier check / write (the pre-commit hook and CI run the check)
- `npm run watch`: rebuild on change; press F5 in VS Code to launch the extension against the colorize fixtures
- `npx changeset`: describe a user-facing change
- Workflow audit: the "Workflow Security" CI job (`.github/workflows/zizmor.yml`) runs zizmor on every `.github/` change. To run it locally, [install zizmor](https://docs.zizmor.sh/installation/), then `zizmor .github/workflows`

## Rules

### Prose and communication

- American English, no em-dashes. Human-facing text (README, changesets, PR descriptions, issue replies) uses plain words and leads with user impact; agent-facing text uses the most precise term.
- A changeset is one short paragraph per user-noticeable change, leading with the visible effect; no mechanism, no internal-only changes, no unmeasured claims.
- No "Generated by" or attribution footers or trailers in commits, PRs, or files.
- A user-facing message (`window.show*Message`) states the problem and the fix in plain language, with no internals.

### Correctness and types

- `tsconfig.json` is `strict`; types are law. No `as any`, non-null `!`, or `@ts-expect-error`, and no new type-assertion casts; remove existing ones in code you touch.
- Public contract, changed only with a major changeset: grammar scope names (themes and other extensions match them), the language id `source.css.styled`, the command id `extension.insertColonOrSemiColon`, and the extension id. Everything else is internal and may be rewritten freely.
- TextMate rules match one line at a time; a rule that needs a newline never matches. Write a rule per line shape (CONTRIBUTING.md, "A line break seems to break the syntax highlighting").
- Grammar regexes are Oniguruma, not JavaScript. `src/patterns.ts` converts POSIX classes for reuse in JS; a grammar change that adds other Oniguruma-only syntax breaks `insertColonCommand` silently.

### Testing and validation

- Every grammar change adds or updates a fixture in `src/tests/suite/colorize-fixtures/` and commits the regenerated `colorize-results/` file. Review every changed token: a first run on a new fixture writes its result and passes without comparing anything, so the committed JSON is the assertion.
- Treat colorize-results drift with suspicion; a token change outside the edited rule is a regression until proven otherwise.
- Bump the pinned VS Code version in `src/tests/runTests.js` deliberately, regenerating and reviewing all results in the same commit.
- A bug fix starts with a red test (fixture or suite test), then goes green.
- Test names read as spec sentences ("activates without an error").

### Inputs and error handling

- Document text is untrusted (any opened workspace file). Regexes run over it must not backtrack catastrophically (no nested or overlapping quantifiers) and should scan a bounded range, not the whole document, per keystroke.
- No empty or log-only `catch`; handle the failure or let it surface.

### Organization and naming

- One provider or command per file in `src/`; `extension.ts` only wires them.
- Grammar regexes live JSON-escaped in `syntaxes/*.json`; decode before editing, re-encode after (CONTRIBUTING.md, "Syntax").
- Never reorder grammar `patterns` arrays for tidiness: TextMate tries rules in order, so order is behavior.
- Split a file past ~4,000 lines.

### Comments and docs

- Comment only a surprise (a workaround, an invariant the types cannot express): one line, at the surprise, saying why. No commented-out code, banners, or bare TODOs; temporary code says "remove when <condition>".
- One fact, one home: change a fact where it lives and grep the repo (docs, comments, tests, workflows) for every older copy in the same change.
- Docs describe current state, never completions or history (CHANGELOG.md is the history).

### Security and data

- The extension makes no network calls and collects no data; keep it that way.
- Releases publish through Marketplace trusted publishing (OIDC). Never add a long-lived publish token or secret.
- Workflow hardening is enforced by zizmor in CI: SHA-pinned actions with a version comment, least-privilege `permissions`, `persist-credentials: false`, no dependency cache in the release job. Depth: [docs/github-actions.md](docs/github-actions.md).
- Package install scripts stay off (npm's `allowScripts` gate); approve one only on demonstrated breakage, with a one-line reason.

### Migrations and data lifecycle

- N/A: no persisted data.

### Performance

- The color provider and the grammar run on every edit. Validate a change to either against the previous code with a microbenchmark on a large file; never trade behavior for speed without a measurement.
- Keep measured figures (timings, sizes) out of docs; state the budget and the command that measures it.

### Git and process

- Every PR with a user-facing change adds a changeset (`npx changeset`); CI, docs, and test-only PRs add none.
- Merging to `main` opens or updates the "Version Packages" PR; merging that PR publishes. Never bump `version` or edit `CHANGELOG.md` by hand.
- A dependency change updates `package-lock.json` in the same commit and is verified with `npm test`.
- Never `git stash`; use a temporary commit. Never force-push `main`.

### Method

- Catalog every instance of a defect's pattern (other grammar rules, other fixtures) before fixing one; fix the class.
- Fix the cause, not the symptom: no regenerating colorize-results to green, no swallowed errors, no disabled checks.
- Ground claims in fresh evidence (run the test, inspect tokens with "Developer: Inspect Editor Tokens and Scope"), and say what was observed versus inferred.
- After deleting code, search for what it left vestigial (fixtures, `.vscodeignore` entries, docs, workflow steps).

### Aesthetic and UX

- N/A for visuals: colors come from the user's theme via scope names. UX rules live under "Correctness and types" (public contract) and "Prose" (messages).

### Domain and stack

- IntelliSense needs a TypeScript 5.x or 6.x tsserver host; TypeScript 7 ships no tsserver and loads no plugins. The repo's `typescript` devDependency is for typechecking only. Depth: [docs/typescript.md](docs/typescript.md).
- Release pipeline facts: [docs/changesets.md](docs/changesets.md).

### Wayfinding and backlog

- GitHub Issues is the tracker; no BACKLOG.md.
- Keep this file a tight index; rule depth goes to `docs/standards/<category>.md` (create it on first need), stack facts to `docs/<tech>.md`.
